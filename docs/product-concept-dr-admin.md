# Концепция развития админки стола ДР

**Статус:** рабочая продуктовая концепция (согласованные направления; детали реализации требуют проверки).  
**Дата фиксации:** 13 октября 2026 года.  
**Источники:** обсуждение продуктовых целей; [фидбэк парков и сотрудников](./feedback-dr-admin.md).

## 1. Problem Statement — проблема

Текущая административная панель стола ДР не адаптирована под рабочие задачи аниматоров.

Сложный интерфейс, недостаточно понятная последовательность действий и отсутствие гибкости при управлении игровыми сценариями препятствуют самостоятельному проведению мероприятия.

**В текущем процессе аниматор вообще не взаимодействует с админкой.** Управление осуществляет сотрудник парка. Для переключения этапов и выполнения других операций аниматор вынужден покидать помещение с детьми и обращаться к администратору парка. Зависимость от второго сотрудника является постоянной составляющей текущего процесса.

Админка не адаптирована под мобильное использование, что дополнительно ограничивает возможность непосредственного управления мероприятием.

## 2. Product Vision — видение продукта

Админка стола ДР — самостоятельный, интуитивно понятный инструмент, который **сопровождает аниматора на каждом этапе мероприятия**, помогает принимать решения в нестандартных ситуациях и позволяет **самостоятельно управлять игровым сценарием** без специальных технических знаний и привлечения сторонних сотрудников.

Продукт должен быть понятен начинающему аниматору после минимального инструктажа и доступен для управления через браузер на личном телефоне.

## 3. Product Goals — цели

1. **Самостоятельность новичка.** Новый аниматор может провести мероприятие после минимального инструктажа, без подсказок и помощи сотрудников парка. Метрика для проверки: доля успешных самостоятельных прохождений сценария.
2. **Снижение ошибок управления.** Сократить число ошибочных действий при запуске и переключении этапов. Метрика: ошибки управления на одно мероприятие / тестовое прохождение.
3. **Ускорение ключевых операций.** Сделать запуск, переход между этапами и другие основные действия быстрее. Метрика: время выполнения ключевых действий.
4. **Устранение зависимости от второго сотрудника.** Аниматору не требуется обращаться за переключением этапов и штатным управлением к администратору парка. Метрика: количество обращений за помощью при проведении мероприятия.
5. **Мобильное управление через браузер.** Аниматор может открыть админку на своем телефоне и управлять праздником. Критерий проверки: выполнение всех необходимых операций в мобильном браузере.

**Примечание:** количественные целевые значения KPI пока не установлены; их необходимо определить после сбора базовых показателей и первых пользовательских тестов.

## 4. Формирование концепции

### 4.1. Изменение модели управления

Планируется не только обновление визуального интерфейса, но и изменение бизнес-процесса:

| Параметр | Сейчас (AS-IS) | Целевая модель (TO-BE) |
| --- | --- | --- |
| Кто управляет админкой | Сотрудник парка | Аниматор |
| Кто переключает этапы | Сотрудник парка по запросу аниматора | Аниматор самостоятельно |
| Взаимодействие аниматора с админкой | Отсутствует | Непосредственное управление |
| Где доступно управление | Существующая админка | Отдельный браузерный интерфейс, прежде всего на телефоне |
| Поддержка прохождения сценария | Требуется участие другого сотрудника | Пошаговое сопровождение и подсказки в интерфейсе |
| Нестандартные ситуации | Ограниченная гибкость переключения этапов | Возможность принимать решения и корректировать ход праздника |

### 4.2. Основные направления

**А. Отделение админки стола ДР от админки проектов.**  
Создать отдельный пользовательский интерфейс, ориентированный на задачи аниматора. Способ технического разделения, интеграции и права доступа еще предстоит определить с разработкой.

**Б. Guided Workflow — сопровождение по сценарию.**  
Интерфейс показывает текущий этап, подсказывает возможное следующее действие и помогает понимать, что происходит во время праздника. Цель — минимизировать необходимость запоминать технические операции.

**В. Гибкое управление сценарием.**  
Нужна возможность переходить между этапами вне жесткой последовательности, включая нестандартные ситуации. Рабочая гипотеза для UX: основной сопровождаемый режим и дополнительное свободное управление. Допустимые переходы и последствия переключений еще нужно проработать.

**Г. Mobile First и казуальный, интуитивный UX.**  
Проектировать интерфейс прежде всего под телефон: понятные названия действий, крупные элементы управления, ясное текущее состояние, минимум лишних операций, защита от критических случайных нажатий.

**Д. Независимость аниматора от сотрудника парка.**  
Ключевые штатные действия должны быть доступны непосредственно аниматору, чтобы ему не требовалось оставлять детей ради управления праздником.

### 4.3. Что подтверждено обратной связью, а что еще нужно проверить

В [собранном фидбэке](./feedback-dr-admin.md) описаны: сложность освоения интерфейса, затруднения с запуском торта и определением нужной кнопки после паузы, зависимость от сотрудников парка, потребность в свободном переключении этапов, недостаток информации об особенностях тем. Эти наблюдения поддерживают выбранные продуктовые направления.

Отдельно зафиксированы проблемы игрового контента и производительности («Города», «Конфеты», реакция стола при большом количестве детей). Их следует учитывать как связанные задачи, **но не считать автоматически частью объема UX-переработки админки**.

Подлежат проверке: детальная карта пользовательского пути, перечень нестандартных ситуаций, границы полномочий аниматора, поведение отдельных тем, техническая реализуемость управления из мобильного браузера.

## 5. MVP — первая тестируемая версия

**Замысел:** подготовить первый рабочий драфт с заложенной логикой сопровождения, на котором тестируемый сможет **полностью пройти сценарий от запуска до завершения без подсказок со стороны**.

### Минимальные условия готовности к тестированию

1. Реализован сквозной путь: подготовка/запуск → этапы проведения → завершение мероприятия.
2. Аниматору доступны основные операции по управлению сценарием, необходимые для тестового прохождения.
3. Интерфейс показывает текущий этап и помогает выбрать дальнейшее действие.
4. Предусмотрено управление порядком этапов и проверка ключевых нестандартных ситуаций.
5. Полный тестовый путь можно пройти через браузер на мобильном телефоне.

### Условие успешности проверки гипотезы

Тестируемый **самостоятельно** выполняет весь сценарий без устных подсказок и привлечения другого сотрудника. Дополнительно фиксируются ошибки, обращения за помощью, затруднения и время выполнения ключевых действий.

**Границы MVP еще не утверждены:** число игровых тем, перечень необходимых операций, нестандартные сценарии и техническая архитектура будут определены после User Journey Mapping (карты пути аниматора) и проверки текущей реализации.

## 6. Следующий продуктовый шаг

Описать реальный процесс проведения праздника **AS-IS** с действиями аниматора и сотрудника парка, затем построить **TO-BE User Journey**: подготовка → запуск → этапы → альтернативные ситуации → финал. На его основе сформировать пользовательские сценарии, UX-требования и границы MVP.
